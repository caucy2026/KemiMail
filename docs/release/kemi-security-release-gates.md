# KEMI Security and Release Gates

This document defines the minimum supply-chain and security evidence required for a KEMI Mail release. It supplements the upstream release process; it does not replace any existing Thunderbird for Android gate.

## Release SBOM boundary

KEMI Mail has one release distribution and one SBOM:

| Distribution | Resolved Gradle configuration |                        Output                         |
|--------------|-------------------------------|-------------------------------------------------------|
| KEMI         | `kemiReleaseRuntimeClasspath` | `app-k9mail/build/reports/sbom/kemi-release.cdx.json` |

The document is CycloneDX 1.7 JSON generated by the pinned CycloneDX Gradle plugin. It describes Gradle's resolved release runtime graph, including transitive components and dependency relationships. Debug, unit-test, Android-test, buildscript, and signing dependencies are outside this boundary.

Run:

```bash
./gradlew :app-k9mail:kemiReleaseSbom
python3 -m unittest discover -s scripts/ci/tests -p 'test_*.py'
bash scripts/ci/validate-kemi-sbom.sh
```

The project validator checks the expected product and app version, a non-empty component graph, reference integrity, absence of random serial numbers, and absence of local paths or credential-shaped fields. The pinned official CycloneDX CLI then validates the document against the 1.7 schema. CI archives only `kemi-release.cdx.json` and fails when it is missing.

`includeBomSerialNumber`, build-environment collection, build-system references, and license text are disabled. This reduces run-specific data and prevents local build details from entering the release evidence. The SBOM is an inventory, not proof that a dependency is vulnerability-free and not SLSA provenance.

## Control responsibilities

|        Control         |                   Trigger                    |                                         What it proves                                          |           What it does not prove            |                             Release evidence                              |
|------------------------|----------------------------------------------|-------------------------------------------------------------------------------------------------|---------------------------------------------|---------------------------------------------------------------------------|
| Dependency Guard       | Every quality workflow and dependency change | The committed KEMI release dependency baseline matches the resolved graph                       | Vulnerability status or license approval    | Passing `dependencyGuard`; reviewed baseline diff when changed            |
| KEMI SBOM gate         | Pull requests and pushes to `main`           | The release runtime graph is machine-readable, policy-valid, schema-valid, and archived         | Artifact provenance or vulnerability status | `kemi-release-sbom` artifact and its GitHub artifact digest               |
| Dependabot             | Weekly, seven-day cooldown                   | Available Gradle, GitHub Action, and script dependency updates are proposed                     | Safe automatic adoption                     | Reviewed PR, dependency baseline diff, tests, and manual regression scope |
| Fluid Attacks SCA      | Weekly and manual                            | Known dependency findings from the pinned scanner image are reported to code scanning           | Absence of unknown vulnerabilities          | Successful run after the release commit; no unresolved blocking finding   |
| Fluid Attacks SAST     | Weekly and manual                            | Static security findings from the pinned scanner image are reported                             | Runtime behavior                            | Successful run after the release commit; no unresolved blocking finding   |
| CodeQL                 | Weekly and manual                            | Java/Kotlin, Python, and Actions queries completed                                              | Full Android runtime or device behavior     | Successful run after the release commit; no unresolved blocking finding   |
| OpenSSF Scorecard      | `main`, weekly, and manual                   | Repository supply-chain posture is measured                                                     | App-level vulnerability status              | Latest result reviewed; regression accepted or fixed                      |
| KEMI regression matrix | Every candidate                              | User-visible, privacy, migration, and dual-screen behavior was exercised on the required matrix | Source or dependency analysis               | Completed matrix and linked defects                                       |

The Fluid Attacks images are pinned by immutable digest in `scripts/ci/run-fluidattacks-scanners.sh`. A scanner update is a security-tool change: update one digest per reviewable pull request, record the upstream release or image date, run both scanners, and inspect result-count changes before merging.

## Vulnerability and dependency update policy

1. A dependency update must not be auto-merged. Review release notes, provenance, license impact, the Dependency Guard diff, the SBOM diff, affected tests, and the regression scope.
2. Critical or High findings affecting a shipped path block release until fixed or proven not applicable with reproducible evidence.
3. Medium findings require an owner, mitigation, and target date. A release exception requires release-owner and security-owner approval and expires within 30 days.
4. Low findings are tracked and reviewed during the next dependency cycle. A severity label never overrides evidence that exploitation is practical.
5. Emergency security updates may shorten the normal bake period, but may not skip dependency resolution, SBOM validation, privacy checks, install/upgrade smoke tests, or sign-off.
6. Before every production candidate, manually run the scheduled SCA, SAST, and CodeQL workflows against the candidate commit if their latest successful run predates it.
7. Never paste credentials, account identifiers, message content, signing configuration, or private scanner output into an issue, release note, SBOM, or public CI log.

## Release decision

A candidate is blocked unless all of the following are true:

- The candidate commit is immutable and recorded.
- Dependency Guard passes and every baseline change is explained.
- The CycloneDX file passes project policy and official schema validation.
- The CI SBOM artifact digest is recorded in the release evidence.
- SCA, SAST, and CodeQL have no unresolved blocking finding for the candidate.
- The KEMI regression matrix is complete with no open Critical or High defect.
- Crash diagnostics contain only the approved fields and no sensitive content.
- The mapping file and signed artifact hashes are stored in access-controlled release storage; keystores and signing properties are never uploaded as CI artifacts.
- A release owner and a security owner approve the evidence, including every time-bounded exception.

Use [KEMI Release Evidence Template](kemi-release-evidence-template.md) for the decision record and [KEMI Regression Matrix](kemi-regression-matrix.md) for device and feature coverage.
